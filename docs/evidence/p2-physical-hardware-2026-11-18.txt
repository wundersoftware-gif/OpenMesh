## 1. Redmi 13C as the client (arm64 hardware)

Topology: the phone runs the VPN; the emulator runs the gateway. Because the
two devices are on the same Wi-Fi, an `adb reverse` on the phone was used to
reach the emulator gateway at `127.0.0.1:8443` (the emulator's gateway socket
was exposed with `adb -s emulator-5554 forward tcp:8443 tcp:8443`).

The phone **did have working Internet over Wi-Fi** during this run. That is
deliberate: it makes the fail-closed run meaningful, because a leak would have
succeeded.

The emulator gateway was stopped, the phone's VPN kept running, and the lab

```text

                    2606:4700:10::6814:179a, 2606:4700:10::ac42:93f3 (8 ms)

FAILED after 34 ms: SocketException: Connection reset
```

The 8 ms DNS line is Android's **device-local resolver cache** (the same answer
was fetched seconds earlier through the tunnel). The HTTP/HTTPS failures are
the important part: with a fully working Wi-Fi uplink, the captured app got
**zero** direct egress. This is the fail-closed property proven on real
hardware, not only on the emulator.

## 2. Redmi 13C as the gateway (arm64 hardware, real Wi-Fi)

Topology: the emulator is the client and dials the phone's LAN address
`192.168.1.58:8443` directly over Wi-Fi. **No `adb forward` and no `adb
reverse` are involved in this path.** The phone accepted the TLS 1.3
connection on its own Wi-Fi interface and exited to the Internet through the
same Wi-Fi.

**Why `10.0.2.2:8080` fails in this topology:** `10.0.2.2` is the Android
emulator's alias for the host loopback. When the gateway is the physical phone,
that address means nothing on the phone's network, so the gateway cannot dial
it. This is a topology mismatch in the lab harness, not a product failure. The
meaningful results here are DNS, the nested TLS 1.3 HTTPS fetch and the policy
denial. The HTTP-through-gateway check is covered by §1, where the gateway is
the emulator and `10.0.2.2:8080` is the correct address.

### 2.3 Identity persistence on the phone

The phone's gateway was stopped and started again on the same install:

```text
gateway listening on 0.0.0.0:8443
fingerprint=503f092856b576808efda29b19503e98fa3069707644cae1addcb4753f09ce8e
```

Same fingerprint, no re-pairing. The emulator client recovered automatically on
the next probe (`Route=SELECTED`, `Internet=VERIFIED`).

Note: the phone and the emulator have **different** identities
(`503f09…ce8e` vs `4667…7ed2`), which is the expected per-device self-signed
certificate. A client pinned to the wrong one is rejected (§4).

## 4. Findings, including lab mistakes

1. **`adb reverse` collides with the gateway port.** While the phone was a
   client, `adb -s <phone> reverse tcp:8443 tcp:8443` created a listening
   socket on the phone's port 8443. Starting the phone gateway at that moment
   failed with `bind failed: EADDRINUSE (Address already in use)`, and the UI
   showed the error. Removing the reverse mapping before starting the gateway
   fixed it. Real deployments do not use `adb reverse`, but the failure mode is
   correctly surfaced rather than hidden.
2. **A stale client VPN can coexist with the gateway.** The phone had its old
   client VPN running (pinned to the emulator's identity, so `NO_ROUTE` with a
   fingerprint mismatch) while also serving as a gateway. The gateway's
   outbound sockets are outside the VPN allowlist, so traffic was unaffected,
   but the test harness stops the client VPN before using the phone as a
   gateway to keep the state clean.
3. **Xiaomi blocks input injection from adb** unless "USB debugging (Security
   settings)" is enabled (requires a Mi account). `adb shell input` returns
   `SecurityException: INJECT_EVENTS`. Screenshots of the phone were therefore
   taken with the screen unlocked by hand, not automated. This does not affect
   the app or the tests.
4. **Device-local DNS cache again.** When the gateway is down, Android can
   still answer a previously seen name from its cache (5–8 ms here, ~20 s on
   the emulator after retries). The packet-level emulator capture in
   `p2-direct-gateway-2026-11-17.txt` §6 proves no DNS packet leaves the device
   outside the tunnel; the cache nuance is documented rather than hidden.

## 5. What this evidence proves

- The P2 client path runs on a physical **arm64-v8a** Android 15 phone:
  TLS 1.3 with certificate pinning, RFC 1929 token authentication, DNS-over-TCP
  through the gateway, nested TLS 1.3 HTTPS and destination-policy denial.
- The P2 gateway path runs on a physical arm64 phone and accepts a real Wi-Fi
  client at `192.168.1.58:8443`, with counters and a persistent identity.
- Fail-closed holds on physical hardware with a working uplink: when the
  gateway is absent or unauthenticated, captured traffic does not leak.
- No central server, no root, no WhatsApp modification.

## 6. What this evidence does **not** prove

- **WhatsApp.** The debug build captures `com.openmesh.testclient`; WhatsApp
  was never installed or run. The release APK targets `com.whatsapp` but is
  unsigned and has not been executed.
- **Two physical phones.** One endpoint was always the emulator. A real
  phone-to-phone run (and the three-phone A → B → C mesh) is still pending.
- **A phone with no Internet at all as the client.** The Redmi had working
  Wi-Fi during the client run; fail-closed was proven by the captured app
  failing while that uplink existed. A truly offline client needs the local
  transport (BLE / Wi-Fi Direct) that is not implemented.
- **A LAN run between two physical phones on different networks** and across
  NAT, mobile data only, captive portals, IPv6-only, etc.
- **mTLS, Keystore storage, quotas, revocation, fuzzing** of the gateway
  surface. See `docs/SECURITY.md` §6.
- Long-run battery, thermal or data-usage behaviour.
