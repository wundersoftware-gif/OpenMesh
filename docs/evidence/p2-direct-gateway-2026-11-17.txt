The `adb forward` is a **lab harness**. On two physical phones on the same
network the client dials the gateway's LAN address directly; no forwarding or
central server is part of the product.

The gateway session token is deliberately not reproduced here. It is a bearer
secret stored in app-private preferences and can be regenerated in the UI.

## 1. Positive path (final artifacts, 17:25 UTC)

Commands (abridged; `$FP` is the pinned fingerprint, `$TOKEN` the gateway
token):

```powershell
adb -s emulator-5554 install -r -t app-debug.apk
adb -s emulator-5556 install -r -t app-debug.apk
adb -s emulator-5556 install -r -t testclient-debug.apk

adb -s emulator-5554 forward tcp:8443 tcp:8443
adb -s emulator-5554 shell am broadcast -a com.openmesh.debug.START_GATEWAY `
  --ei port 8443 -n com.openmesh.app.debug/com.openmesh.app.DebugControlReceiver

adb -s emulator-5556 shell appops set com.openmesh.app.debug ACTIVATE_VPN allow
adb -s emulator-5556 shell am broadcast -a com.openmesh.debug.START_VPN `
  --es mode gateway --es host 10.0.2.2 --ei port 8443 `
  --es fingerprint $FP --es token $TOKEN `
```

## 2. Fail-closed when the gateway disappears (17:32 UTC)

Gateway stopped while the client VPN stayed up, then the lab client was run
again:

```text
vpn=VpnStatus(phase=NO_ROUTE, targetPackage=com.openmesh.testclient, link=UP,
route=NONE, internet=FAILED, gatewayId=null, hops=null,
remoteGateway=true, engineRunning=true,
probeDetail=gateway unreachable or untrusted:
SSLHandshakeException: connection closed)

DNS example.com -> 172.66.147.243, 104.20.23.154 (20257 ms)
HTTP GET http://10.0.2.2:8080/health
FAILED after 528 ms: SocketException: Connection reset
HTTPS GET https://example.com/
FAILED after 1050 ms: SocketException: Connection reset
HTTP GET http://10.0.2.2:8081/health (expected deny)
expected deny after 520 ms: SocketException: Connection reset
```

Note the DNS line: the query was answered after ~20 s from Android's
**device-local** resolver cache, after the tunnel attempts failed. §6 proves no
DNS packet left the device on the underlying network. No captured application
packet reached the real network: every HTTP/HTTPS fetch failed and the client
had no connector. This is fail-closed for traffic, with a device-local DNS
cache nuance that is documented rather than hidden.

## 3. Wrong gateway token (earlier round, 15:24 UTC)

Gateway running, client configured with an incorrect token:

```text
phase=NO_ROUTE, link=UP, route=NONE, internet=FAILED,
probeDetail=gateway unreachable or untrusted:
Socks5Exception: SOCKS5 authentication failed
```

Gateway counters increased `denied` while `accepted` stayed at zero for that
attempt. TLS 1.3 succeeded (the certificate pin was correct); the RFC 1929
token was rejected, so no SOCKS request was served.

## 4. Wrong certificate fingerprint (earlier round, 15:27 UTC)

Client configured with a different 32-byte fingerprint:

```text
phase=NO_ROUTE, link=UP, route=NONE, internet=FAILED,
probeDetail=gateway unreachable or untrusted: SSLHandshakeException:
gateway certificate fingerprint mismatch; expected 0000...0001,
got 46676594f8054ae4f0dfc6910fbe74e1904ddf65121419eef8541627fae17ed2
```

This is the pinning check, not hostname verification: the certificate is
self-signed, and the full SHA-256 fingerprint must match exactly.

## 5. Identity persistence

The gateway was stopped and restarted several times on the same install. It
loaded the identity from `filesDir/openmesh-gateway-identity.p12` and logged the
same fingerprint every time; clients did not need to re-pin.

## 6. Packet proof: no DNS or traffic leaves the device outside the tunnel

Eight packets, all `Out` on `tun0`: every query entered the tunnel and was

retry pattern explains the ~20 s DNS time: four attempts, all inside the
tunnel, then a local cache answer.

## 7. A lab-harness failure that is worth recording

During the first final-artifact run the host test server on port 8080 had
crashed, so `http://10.0.2.2:8080/health` failed with a connection reset. This
was diagnosed on the host (`Invoke-WebRequest http://127.0.0.1:8080/health`
refused) and the server was restarted; the rerun in §1 shows HTTP 200. The
gateway counted it as a denied connection because the dial failed, which is why
the lab keeps a **live** decoy on 8081: a dead-port "deny" and a policy deny look
identical from the client, and only one of them proves the policy.

## 8. What this evidence does not prove

- WhatsApp itself was never installed or run. The debug build captures
  `com.openmesh.testclient` by design.
- Both endpoints are emulators on one host, not two physical arm64 phones.
- The transport between emulators used an `adb forward`; a LAN run is still
  required.
- No IPv6 destination was exercised end to end (AAAA answers were returned,
  but the fetches used IPv4).
- No relay, multi-hop, BLE or Wi-Fi Direct path exists.
- Android's device-local DNS cache can answer a query while the gateway is
  down (§2); no packet leaves the device outside the tunnel, but the answer is
  not freshly validated by the gateway.
- The gateway has not been exposed to a hostile network: no fuzzing, no quotas,
  no revocation, no mutual TLS.
- The user-visible app is a P2 lab: the gateway is a foreground service, the
  token lives in app-private preferences (not the Android Keystore), and the
  debug control receiver is exported in debug builds only.

The honest summary is: **A → C over authenticated TLS 1.3 works in the
emulator, nothing leaks when C is absent (packet-level proof), and it fails
closed when C is unauthenticated or untrusted.** The three-phone WhatsApp mesh
remains untested and unimplemented.
